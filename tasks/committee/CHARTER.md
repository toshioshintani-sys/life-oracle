| 担当 | 主業務 | 報告頻度 | 調査手段 |
|---|---|---|---|
| 🧭 UX | 市場の新技術・競合・SNSトレンドを調査し、診断/結果画面への適用案を出す | 毎日 | Web検索 |
| ✍️ コンテンツ | 質問・選択肢・結果文の「答えやすさ」を被験者目線で追求、心理学/行動経済学の噛み砕き | 隔日 | 質問ファイル+Web検索 |
| ⚙️ エンジン | 速度・挙動エラー・回帰の監視と原因→修正提案 | 毎日 | CI状態 |
| 📊 データ | GA4の完走率・離脱・結果分布を読み、理由と改善案を各担当に投げかける | 毎日 | GA4 |
| 🔍 SEO | アナリティクス/検索トレンドを読み、狙うキーワードと導線を設計 | 毎日 | note指標+Web検索 |

**全担当の鉄則:** 調べて終わりにしない。必ず「理由」と「具体的な改善提案」をセットで出す。

## 日次サイクル

| 時刻 | 動き | 実体 |
|---|---|---|
| 08:00 JST | システム/数値の監視レポート（別系統） | `daily_report.py` → Slack |
| 10:00 JST | 各担当が調査し `reports/YYYY-MM-DD/<担当>.md` にコミット | `committee.py --phase research` |
| 14:00 JST | 会議。議長（秘書）が持ち寄りレポートを統合し議事録を生成 | `committee.py --phase meeting` |

会議の成果（議事録）は Slack に投稿され、`LEDGER.md` に追記される。

### 継続審議
その日に決まらない論点は **翌日に持ち越す**。`LEDGER.md` が前回までの継続審議を保持し、
翌日の会議に自動で持ち込まれる。

### 俊雄さんへの報告（秘書の役割）
議事録には必ず **「俊雄さんへの依頼（理由つき）」** セクションがある。
俊雄さん自身の実行が必要なもの（GitHub Secrets 追加、note 公開、判断が必要な分岐など）は、
**なぜ必要かを添えて** 提案する。実行が不要な日は「なし」。

## ガバナンス（暴走の防止）

- 秘書（Claude）が重大変更を提案するときは **proposal-stress-test スキル**（Step0→A→B→C）で自己検証する。
- `git push` の前に **stress-test ゲート**（`.claude/pre-push-stress-gate.sh`）が必ず挟まる。
  proposal-stress-test を実施し俊雄さんの承認を得たうえで `.claude/.stress-test-ok` を作成しないと push できない。
- **PR は俊雄さんの承認なしにマージしない。**
- 絶対に触らないデータ（処方箋2016件・偉人16名・cognitiveFunctionMap・光と影の名前）への
  変更提案は全担当で禁止。

## 運用メモ

- 自動化は `main` にマージ後にスケジュール発火する（GitHub の仕様）。
  マージ前は各ワークフローの「Run workflow」（workflow_dispatch）で手動テストできる。
- モデルは既定 `claude-opus-4-8`（最高品質）。コスト優先なら GitHub Secrets に
  `COMMITTEE_MODEL=claude-sonnet-4-6` を設定すると切り替わる。
- 必要な GitHub Secrets:
  - `ANTHROPIC_API_KEY`（必須・既存）
  - `SLACK_WEBHOOK_URL`（必須・既存。daily-report と共用）
  - `GA4_PROPERTY_ID` / `GOOGLE_CREDENTIALS_JSON`（任意・data担当の実データ化）
  - `COMMITTEE_MODEL`（任意・モデル切替）
