# 📊 データ担当 日次レポート — 2026-06-07

## 調査サマリ（今日わかったこと・3〜6点、箇条書き）

- **GA4 未連携のため、現状すべての行動データがブラックボックス**。完走率も離脱点も結果分布も一切わからず、改善は全て「勘」で回っている状態。
- 今いちばん見るべき指標は、議論の余地なく **「設問ごとの離脱率（=どこで脱落するか）」** と仮説立てした。完走率は「結果（症状）」、離脱点は「原因（病巣）」だから。
- 次点で見るべきは **「結果タイプ分布の偏り」**。16タイプ（光と影）のうち特定タイプに過度に偏っていれば、診断ロジックか質問設計に歪みがある可能性のシグナルになる（※ロジック自体は触らず、まず観測する）。
- 北極星「SNSで自然発生的に噂される」に対し、現状は **計測がないので北極星への距離を1ミリも測れていない**。これが最大の構造的リスク。
- GA4 有効化に必要なものは2つだけ（`GOOGLE_CREDENTIALS_JSON` と `GA4_PROPERTY_ID`）。技術的ハードルは低く、**やっていないだけ** の状態。

## なぜ重要か（理由）

- **離脱点を見るべき理由**: 完走率が仮に40%だったとして、「全設問で均等に薄く落ちる」のと「Q5で一気に半分落ちる」のでは打ち手が真逆。前者は全体の体験テンポ、後者はQ5単体の改善。離脱点がわからないと、改善対象を特定できず工数が霧散する。
- **結果タイプ分布を見るべき理由**: 「凄い」と言わせる体験は、結果が当人に深く刺さってこそ。もし16タイプが極端に偏るなら、ユーザーは「みんな同じ結果が出る」と感じ、SNSでの自慢・シェア動機（＝北極星）が死ぬ。分布の健全性はバイラル可能性の先行指標。
- **計測自体を持つべき理由**: 噂が立ったかどうかは、流入元（referral / social）の変化で最も早く検知できる。GA4がなければ、せっかく噂が立っても「立ったこと」に気づけず、波に乗る初動を逃す。

## 改善提案（具体・実装可能・優先度つき）

### 優先度【最高】GA4 計測を本日中に有効化する
1. GCP でサービスアカウントを作成 → JSON キーを発行。
2. GA4 管理 > プロパティアクセス管理 で、そのサービスアカウントのメールアドレスを「閲覧者」権限で追加。
3. GitHub の対象リポジトリ > Settings > Secrets and variables > Actions に以下を登録:
   - `GOOGLE_CREDENTIALS_JSON` … 発行したキーJSONの中身をそのまま貼り付け
   - `GA4_PROPERTY_ID` … GA4管理画面のプロパティ設定で確認できる数値ID（`G-` で始まる測定IDではなく、数値の方）
4. 設定後、翌日の自分の分析ジョブが実データを拾えるか検証する。

### 優先度【高】計測有効化と同時に「設問単位イベント」を仕込む
- 各設問の表示・回答完了を `step_view` / `step_complete`（パラメータに設問番号）として送信。
- これで初めて「Q何番で落ちるか」が見える。**完走/未完走の2値だけでは離脱点が永遠にわからない** ので、ここを最初から設計する。

### 優先度【中】結果到達時イベントで結果タイプを記録
- 結果表示時に `result_view`（パラメータ: 結果タイプ）を送信。分布の偏りを観測する。
- ※あくまで観測のみ。cognitiveFunctionMap・名前・処方箋には一切触れない。

### 優先度【中】流入元の定点観測ダッシュボードを用意
- 北極星検知のため、`session_source` / `session_medium` を毎日見る簡易ビューを作る。本人のX/note以外からの social/referral 流入の増加が、噂の最初の足跡。

## 確信度と次の一手

- **「離脱点が最優先指標」**: 確信度【高】。データの構造上、原因特定には設問単位の観測が必須であることは普遍。
- **「GA4を入れるべき」**: 確信度【高】。技術コストが低く、得られる情報量が桁違い。
- **「結果タイプが偏っている」という仮説そのもの**: 確信度【低】。実データがないため偏りの有無は完全に未検証。
