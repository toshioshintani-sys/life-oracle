# 📊 データ担当 日次レポート — 2026-06-06

## 調査サマリ（今日わかったこと・3〜6点、箇条書き）

- **GA4 が未連携のため、現状すべての行動データが「見えていない」状態**。完走率も離脱点も結果分布も、すべて推測でしか語れない。これは「凄いと言われる体験」へ近づいているかを定点観測できないことを意味し、最優先で潰すべき欠損。
- いま最初に見るべき指標を1つに絞るなら **「設問単位の離脱率（ファネル）」** だと考える。完走率は結果（症状）であって、原因（どこで脱落したか）が分からないと改善アクションに繋がらないため。
- 次点で見るべきは **「結果タイプ分布の偏り」**。特定の光/影タイプに極端に集中している場合、診断ロジックではなく「設問の選択肢の引力」に偏りが出ている可能性があり、体験の多様性＝シェアされる驚きを損なう。
- **完走率は単独では誤読を招く指標**。完走率が高くても「結果が刺さらず無言で閉じる」なら北極星（自然発生的な言及）に届かない。完走率×結果直後のシェア/スクショ相当行動をセットで見る前提を最初から設計すべき。
- GA4 計測は「あとから過去を遡れない」ため、**今日設定しないと今日のデータは永遠に失われる**。設定の遅れが累積コストになる構造。

## なぜ重要か（理由）

- **設問単位の離脱率を最優先にする理由**：完走率が60%だったとして、「設問3で40%落ちている」のか「設問1〜10で均等に少しずつ落ちている」のかでは打ち手が真逆。前者なら設問3だけ直せばいい（低コスト・高効果）。後者は診断全体の長さ・テンポの問題。原因の所在が分かる指標こそ、各担当に課題を投げられる。
- **結果タイプ分布を見る理由**：「凄い」と言いたくなる体験は、ユーザーが「自分だけの結果が出た」と感じることで生まれる。分布が一部タイプに偏っていれば「みんな同じ結果じゃん」とシェア動機が死ぬ。分布の健全さ＝バズの種の多様性。
- **完走率を単独指標にしない理由**：完走＝成功ではない。最大目的は「誰かに言いたくなる」こと。完走後の沈黙は最悪の状態（時間を使わせて何も残らない）。完走率は入口指標、シェア相当行動が出口指標。

## 改善提案（具体・実装可能・優先度つき）

**【優先度：最高】GA4 計測を今日中に有効化する**
1. Google Cloud でサービスアカウントを作成 → JSON キーを発行
2. GA4 管理画面 → プロパティ設定 → **プロパティID（数字9桁）** を控える
3. GitHub リポジトリ → Settings → Secrets and variables → Actions に以下を登録：
   - `GOOGLE_CREDENTIALS_JSON`（サービスアカウントJSONの中身を丸ごと）
   - `GA4_PROPERTY_ID`（数字のみ。`properties/` は付けない）
4. GA4 のデータアクセス権限に、上記サービスアカウントのメールアドレスを「閲覧者」で追加
5. 翌日のジョブで疎通確認（取得件数が0でないこと）

**【優先度：高】計測する前に「測る対象」をイベント設計する**
- `quiz_start` / `quiz_question_view`（設問番号をパラメータに）/ `quiz_complete` / `result_view`（結果タイプをパラメータに）/ `result_share_intent`（シェアボタン押下・スクショ相当）
- これがないと、GA4 を繋いでも「設問単位の離脱」も「結果分布」も取れない。**繋ぐこと自体が目的化しないよう、設計を先に固める**。

**【優先度：高】UX担当への先回り課題**
- 計測が立ち上がるまでの間、設問1の表示〜最初の選択までを自分で5回触り、「どこで指が止まるか」を体感ログとして残す。数字が来たときに「やはりここか」を即断できる準備。

**【優先度：中】コンテンツ担当への問い**
- 結果直後の画面に「言いたくなる一言」が含まれているか。完走後の沈黙を防ぐのはコピー。分布データが出る前に、結果画面の出口設計を点検依頼。
