# 📊 データ担当 日次レポート — 2026-06-06

## 調査サマリ（今日わかったこと・3〜6点、箇条書き）

- **GA4 未連携のため、現状すべての行動データが「測れていない」**。完走率も離脱点も結果分布も一切不明で、改善判断が「勘」で回っている状態。
- 計測がゼロの今、最優先で見るべき単一指標は **「診断完走率（開始 → 結果表示の到達率）」**。これが全KPIの分母であり、北極星「思わず人に言いたくなる」の前提条件（=結果まで辿り着けないと語りようがない）だから。
- 次点で見るべきは **「設問単位の離脱率（どの設問で脱落するか）」**。完走率が低い時、原因を特定するための解像度を持つのはこの指標だけ。
- 結果タイプ分布は重要だが **優先度は3番目**。完走者が十分溜まって初めて「偏り」が意味を持つため、データ量が無い初期は判断材料にならない。
- 「凄いと言いたくなる」の定量代理指標として **「結果ページ到達後のシェアボタン押下／URLコピー率」** を最初から仕込むべき（後付けは取りこぼす）。

## なぜ重要か（理由）

- **完走率**：診断アプリの体験は「結果」で完結する。途中離脱したユーザーは感動も言及も生まれない。完走率が北極星到達の天井を決める。仮に完走率40%なら、SNS拡散の母数を6割捨てている。
- **設問別離脱**：完走率という「結果」だけでは打ち手が出せない。「設問5で30%落ちる」と分かって初めて、UX担当に「設問5の負荷を見て」、コンテンツ担当に「設問5の問いが重い／意味不明では」と課題を投げられる。データ担当の本領は**課題の名指し**にある。
- **シェア計測**：自然発生的言及（=北極星）の最も近い一次シグナル。SNSエゴサより早く、結果のどのタイプが「言いたくなる」かを定量で掴める。
- **結果タイプ分布（後回しの理由）**：n=20の偏りは偏りに見えてただのノイズ。分母が育つ前に分布を見ると誤った結論（特定タイプを「弾いてる」等）に飛びつくリスクがある。

## 改善提案（具体・実装可能・優先度つき）

### 優先度【最高】GA4 計測を今日中に有効化する
1. GA4 プロパティを作成 → **測定ID（G-XXXX）** と **プロパティID（数字9桁）** を取得。
2. Google Cloud でサービスアカウントを作成し JSON キーを発行（Data API 用）。
3. GitHub の **Settings → Secrets and variables → Actions** に以下を登録：
   - `GA4_PROPERTY_ID`（数字のプロパティID）
   - `GOOGLE_CREDENTIALS_JSON`（サービスアカウントJSONを丸ごと貼付）
4. GA4 の該当プロパティ「プロパティ アクセス管理」に、サービスアカウントのメールアドレスを **閲覧者**で追加（これを忘れると403で読めない）。
5. 疎通確認：`runReport` で過去7日 `screenPageViews` を1本叩いて値が返るか検証。

### 優先度【高】カスタムイベントを最初から3つだけ仕込む
- `quiz_start`（診断開始）
- `quiz_question_view`（パラメータ `q_index` で設問番号を持たせる）← **離脱点特定の生命線**
- `quiz_complete`（結果表示到達）
- ※結果ページに `result_share_click` も追加。設計はシンプルに、4イベント以上は初期は増やさない。

### 優先度【中】完走率ダッシュボードの定義を先に決めておく
- 完走率 = `quiz_complete` ユニークユーザー ÷ `quiz_start` ユニークユーザー。
- 設問別離脱率 = 各 `q_index` の到達数を漏斗で並べ、隣接設問間の脱落%を算出。
- データが溜まる前に**定義を固定**しておくことで、初週の数字から即座に課題を名指しできる。

### 優先度【低・データ蓄積後】結果タイプ分布の偏り監視
- 完走者 n≥100 を超えてから着手。偏りが出ても、まずは「設問の聞き方」起因かエンジン起因かを切り分けてから各担当へ投げる。
