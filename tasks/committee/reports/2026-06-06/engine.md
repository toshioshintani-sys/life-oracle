## なぜ重要か（理由）

- **検知できない劣化は最悪の劣化**：体感速度や初動の軽さは UX 品質に直結し、SNS で「凄い」と言われる体験の土台。ここが静かに落ちると、北極星（自然発生的な口コミ）から遠ざかる。
- **CI 停止＝安全網の不在**：Netlify は自動デプロイなので、検査なしで本番に届く。1 回の不用意な変更が「初回ロードが重い」体験を全ユーザーに配り得る。
- **数値の連続性がないと判断ができない**：単発の計測値は「速い/遅い」を語れない。時系列がないと「回帰の兆候」という今日の任務自体が成立しない。
- **「失敗 0」の誤読は意思決定を歪める**：シグナル無を健全と勘違いすると、必要な手当てを先送りする。

## 改善提案（具体・実装可能・優先度つき）

1. **【優先度：高】CI が本当に止まっているかの切り分け（今日中・5分）**
   - GitHub の Actions タブで「ワークフローが無効化されていないか」「最後の push がいつか」を確認。
   - 原因が「push がない」のか「ワークフロー無効」なのかで対処が分かれる。まず事実確定。

2. **【優先度：高】push 時の最小ビルドチェックを 1 本だけ用意（最小の修正）**
   - `npm ci && npm run build` が通るかだけの軽いジョブを 1 本。大規模 CI は不要。
   - 目的は「`src/App.jsx` の変更が本番に無検査で届かない」最低ラインの確保。

3. **【優先度：中】stress_test.mjs を手動でいいので「基準値」を 1 回取る**
   - 測るべき指標を具体指定：
     - 初回バンドル読込（main chunk の transfer size と評価時間）
     - 診断ロジック 1 回実行の所要時間（処方箋データ参照を含む全体）
     - 連続 50 回実行時の平均・最悪値（引っかかり = 最悪値で出る）
   - この値を `baseline.json` として保存し、次回比較の起点にする。

4. **【優先度：中】ビルド成果物サイズのログ化**
   - `dist` のサイズと chunk 数を build 後に出力。サイズ膨張は初動の重さの先行指標。

5. **【優先度：低】週次で stress_test を回す案**
   - 安定したら週1自動実行へ。今日は提案のみ、まず手動計測を優先。
